## 2026-05-17 - Avoid cryptographic rng for general simulations
**Learning:** The codebase was using `secrets.SystemRandom().randint()` for generating call metrics (duration, waves, intervals) which is a cryptographic operation reading from system entropy (`/dev/urandom`). This adds massive overhead to rapid generation in large-scale simulation threads compared to a pseudo-random number generator.
**Action:** Use standard `random.randint()` for statistical/simulation randomization tasks where cryptographic security is not required, resulting in up to 5-6x speedup in standalone number generation overhead.
## 2026-05-18 - Avoid eager evaluation of is_alive() on thread collections
**Learning:** Eagerly evaluating `is_alive()` on lists of thread-based objects (e.g., using list comprehensions like `[not thread.is_alive() for thread in threads]`) introduces significant overhead because it creates a full list and calls `is_alive()` on every thread before any short-circuiting logic can run. In our profiling, a list comprehension approach took ~0.11s compared to a short-circuit loop or generator taking <0.01s for the same number of evaluations.
**Action:** Prefer passing the raw thread list and using an explicit loop with short-circuiting or a generator expression (e.g., `all(not thread.is_alive() for thread in threads)`) to minimize unnecessary thread state checks.
